Depends where:

- **Locally in `.env.local`**, quotes are optional either way works fine, `dotenv` handles both. I've been using quotes in this project for consistency (e.g. `DATABASE_URL="file:./dev.db"`), but a Postgres connection string works unquoted too.
- **In Vercel's dashboard**, paste it **without** quotes. Just the raw string, like:
  ```
  postgres://user:password@host/dbname?sslmode=require
  ```
  If you wrap it in quotes there, Vercel stores the quote characters as literally part of the value, and Prisma will fail to parse the connection string since it'll start with an actual `"` character.

So: quotes optional locally, no quotes when pasting into Vercel's env var fields.

Here's the full architecture context, structured so it's easy to hand to ChatGPT for a diagram:

---

**System: AzaisAi Rebuild — AI video/image generation web app**

**High-level:** A Next.js full-stack app (frontend + API routes in one codebase) backed by Postgres, with two external AI providers doing the actual generation work. No separate backend service, everything runs as Vercel serverless functions.

**Layers / components:**

1. **Client (Browser)**
   - React UI (Next.js App Router pages): Landing, Auth (signup/login), Video Studio, Image Studio, History, static pages (About/Contact/FAQ/Pricing/Privacy/Terms)
   - `GenerationToastWatcher`: a global component polling for pending job completion, shows a toast notification from anywhere in the app

2. **Server (Next.js API Routes, on Vercel serverless functions)**
   - `/api/auth/request-code`, `/api/auth/verify-code`, `/api/auth/logout` — passwordless email+OTP auth
   - `/api/generate/image` — synchronous: calls Pollinations, returns immediately
   - `/api/generate/video` — asynchronous: submits a job to Pixazo, stores the job reference, returns immediately (does NOT wait for completion)
   - `/api/generations/[id]` — polled by the client every few seconds; if a video job is still "processing," this route does one quick status check against Pixazo and updates the database if it finished
   - `/api/contact` — saves contact form submissions

3. **Database (Postgres, via Prisma ORM)**
   - `User` (id, email, creditsBalance)
   - `LoginCode` (hashed OTP codes, expiry)
   - `CreditTransaction` (ledger: grants, charges, refunds)
   - `Generation` (id, type [image/video], prompt, status [processing/succeeded/failed], resultUrl, externalRef [Pixazo job polling URL], costCredits)
   - `ContactMessage`

4. **External AI providers**
   - **Pollinations** (image.pollinations.ai) — free image generation, single request/response, no auth key strictly required. Returns an image directly at a stable, cacheable URL; that URL itself is stored as the result (no file download/re-hosting needed)
   - **Pixazo** (gateway.pixazo.ai) — free video generation via the LTX model, submit-then-poll pattern: POST returns a job ID + polling URL, GET on that URL returns status until COMPLETED, at which point it gives a permanent result URL (hosted on Cloudflare R2)

5. **Session/Auth**
   - Signed HTTP-only cookie (iron-session), not a database-backed session table
   - Email OTP: 6-digit code hashed and stored with expiry; verified codes create/look up a `User` and set the session

**Key data flows:**

- **Sign up/login:** Client → `/api/auth/request-code` (creates hashed code in DB) → user enters code → `/api/auth/verify-code` (validates, creates/finds User, sets session cookie)
- **Image generation:** Client → `/api/generate/image` → holds credits → calls Pollinations → on success, charges credits + saves Generation row with Pollinations' own URL as resultUrl → returns to client synchronously
- **Video generation:** Client → `/api/generate/video` → holds credits → submits job to Pixazo → saves Generation row (status=processing, externalRef=polling URL) → returns immediately (202) → client polls `/api/generations/[id]` repeatedly → each poll checks Pixazo once → on completion, charges credits and updates the row → client displays result + toast notification fires globally

**Notable architectural decisions (useful context for the diagram):**

- No long-running server tasks anywhere: the video "job" is driven entirely by repeated short client polls hitting a fast serverless function each time, not a background worker, because Vercel functions can't run for the 1-2 minutes a video takes.
- No local file storage: both providers' own URLs are used directly as permanent results, since Vercel's filesystem isn't writable/persistent at runtime.
- Credits are held at request time and only finalized (charged) on success or released (refunded) on failure, tracked as an append-only ledger (`CreditTransaction`), not just a mutable balance.
